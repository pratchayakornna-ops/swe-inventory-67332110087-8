### จุดที่ 1: การขายแบบกลุ่มขาดคุณสมบัติ Atomicity (Partial Deduction Bug)
- **ตำแหน่ง:** เมธอด `sell_batch()`, บรรทัดที่ 16 - 22
- **ปัญหาคืออะไร:** เมธอดวนลูปเรียก `self._inv.sell(name, amount)` ทีละรายการทันที หากคำสั่งซื้อมี 3 รายการ แล้วรายการที่ 1 ตัดสต็อกสำเร็จ แต่รายการที่ 2 สต็อกไม่พอจนเกิด `ValueError` โค้ดจะหยุดทำงานกลางคัน ส่งผลให้สต็อกของรายการที่ 1 ถูกตัดไปแล้วโดยไม่มีการคืนค่า (Rollback) ทำให้ข้อมูลในคลังไม่ตรงกับความเป็นจริง
- **กรณีที่ทำให้พัง (Concrete Example):**

- **ข้อเสนอแก้:** ทำการตรวจสอบสต็อกของทุกรายการใน `orders` ให้ผ่านทั้งหมดก่อน (Validation Phase) หรือใช้กลไกบันทึกประวัติเพื่อ Rollback คืนสต็อกของรายการที่ตัดไปแล้ว หากเกิด Exception ในลูป

### จุดที่ 2: เมธอดจองสต็อกคืนค่าเสมือนสำเร็จเมื่อเงื่อนไขไม่ผ่าน และเสี่ยงเกิด KeyError

### จุดที่ 3: ค้นหาสินค้าตามช่วงราคาไม่รวมค่าที่ขอบเขตปลาย (Off-by-boundary / Exclusive vs Inclusive)
- **ตำแหน่ง:** เมธอด `items_in_price_range()`, บรรทัดที่ 34 - 40
- **ปัญหาคืออะไร:** Docstring ระบุชัดเจนว่า *"คืนรายชื่อสินค้าที่ราคาอยู่ในช่วง [low, high]"* ซึ่งเครื่องหมายวงเล็บก้ามปู `[...]` ในทางคณิตศาสตร์หมายถึงช่วงปิด (Closed Interval: รวมค่าปลายทั้ง `low` และ `high`) แต่โค้ดกลับใช้ `if low < item.price < high:` (ช่วงเปิด Strictly Greater/Less Than)
- **กรณีที่ทำให้พัง (Concrete Example):**
  - คลังมีสินค้า `"Book"` ราคา 100.0 บาท, `"Pen"` ราคา 500.0 บาท
  - เรียก `items_in_price_range(100.0, 500.0)`
  - ผลที่ได้: `[]` (ได้ลิสต์ว่างเปล่า ทั้งที่ควรได้ `["Book", "Pen"]`) สินค้าที่มีราคาตรงกับขอบเขตพอดีจะตกหล่นหายไปจากรายงานทั้งหมด
- **ข้อเสนอแก้:** ปรับเงื่อนไขเป็น `if low <= item.price <= high:`

- **ตำแหน่ง:** เมธอด `low_stock_report()`, บรรทัดที่ 43 - 49
- **ปัญหาคืออะไร:** Docstring ระบุว่า *"คืนรายชื่อสินค้าที่ stock ต่ำกว่าหรือเท่ากับเกณฑ์"* (`<= LOW_STOCK_THRESHOLD`) แต่โค้ดใช้ `if item.quantity < self.LOW_STOCK_THRESHOLD:`
- **กรณีที่ทำให้พัง (Concrete Example):**
  - สินค้า `"USB Cable"` มีจำนวนคงเหลือ 5 ชิ้น พอดีกับเกณฑ์ `LOW_STOCK_THRESHOLD = 5`
  - เรียก `low_stock_report()`
  - ผลที่ได้: `"USB Cable"` ไม่ปรากฏในรายงานเตือน ทำให้พนักงานไม่ทราบว่าของลดลงมาถึงระดับที่ต้องสั่งเติมแล้ว
- **ข้อเสนอแก้:** ปรับเงื่อนไขเป็น `if item.quantity <= self.LOW_STOCK_THRESHOLD:`

### จุดที่ 5: เกิด Race Condition และ Lost Update จากการอ่านค่านอก Lock (Concurrency Bug)
- **ตำแหน่ง:** เมธอด `concurrent_restock()`, บรรทัดที่ 52 - 57
- **ปัญหาคืออะไร:** บรรทัดที่ 54 `current = self._inv._items[name].quantity` ถูกอ่าน **นอกบล็อก `with self._lock:`** ทำให้การอ่านค่าไม่มีการปกป้อง หากมี 2 เธรดทำงานพร้อมกัน เธรดทั้งสองจะอ่านได้ค่า `current` เดียวกัน จากนั้นสลับกันเข้าล็อกเพื่อบวกเพิ่ม ทำให้ยอดการเติมสต็อกของเธรดหนึ่งสูญหายไปทันที (Lost Update)
- **กรณีที่ทำให้พัง (Concrete Example):**
  - สินค้า `"RAM"` มีสต็อกเริ่มต้น 10 ชิ้น
  - Thread 1 เติม 5 ชิ้น และ Thread 2 เติม 3 ชิ้น พร้อมกัน
  - Thread 1 อ่าน `current = 10`
  - Thread 2 อ่าน `current = 10` (ก่อนที่ Thread 1 จะเขียนเสร็จ)
  - Thread 1 เข้าล็อก เขียน `10 + 5 = 15`
  - Thread 2 เข้าล็อก เขียน `10 + 3 = 13` ทับค่า 15 ทันที
  - ผลลัพธ์: สต็อกกลายเป็น 13 ชิ้น แทนที่จะเป็น 18 ชิ้น (สต็อกสูญหาย 5 ชิ้นเงียบ ๆ)
- **ข้อเสนอแก้:** 
  1. ย้ายการอ่านค่าเข้าไปอยู่ภายในบล็อก `with self._lock:` หรือ
  2. เรียกใช้เมธอด `self._inv.restock(name, amount)` ของคลาส Inventory โดยตรง ซึ่งมีการ validate ข้อมูลพร้อมอยู่แล้ว

### จุดที่ 6: สูตรคำนวณมูลค่าเฉลี่ยต่อชิ้นผิดความหมาย และเสี่ยง ZeroDivisionError
- **ตำแหน่ง:** เมธอด `average_unit_value()`, บรรทัดที่ 60 - 64
- **ปัญหาคืออะไร:**
  1. **สูตรผิดความหมาย:** Docstring ระบุว่า *"คืนมูลค่าเฉลี่ยต่อชิ้นของสินค้าทั้งคลัง"* (Average Unit Value) ซึ่งต้องนำ `มูลค่ารวมทั้งหมด / จำนวนชิ้นสินค้าทั้งหมดในคลัง` แต่โค้ดกลับหารด้วย `len(self._inv._items)` ซึ่งเป็นจำนวนชนิด/รายการสินค้า (Number of SKUs) ไม่ใช่จำนวนชิ้น
  2. **หารด้วยศูนย์ (ZeroDivisionError):** หากคลังสินค้ายังไม่มีสินค้าเลย (`len == 0`) หรือจำนวนชิ้นรวมเป็น 0 บรรทัดคำนวณจะ Crash ทันที
- **กรณีที่ทำให้พัง (Concrete Example):**
  - กรณีที่ 1: คลังมีสินค้า 2 ชนิด คือ `"ยางลบ"` (100 ชิ้น ชิ้นละ 10 บาท = 1,000 บ.) และ `"ปากกา"` (1 ชิ้น ชิ้นละ 100 บาท = 100 บ.) รวมมูลค่า 1,100 บาท มีของทั้งหมด 101 ชิ้น (เฉลี่ยชิ้นละ 10.89 บาท) แต่โค้ดนำ 1,100 / 2 ได้ค่าเฉลี่ยชิ้นละ **550 บาท** ซึ่งผิดพลาดมหาศาล
  - กรณีที่ 2: คลังว่างเปล่า (`self._inv._items = {}`) เรียก `average_unit_value()` จะเกิด `ZeroDivisionError: division by zero` ทันที
- **ข้อเสนอแก้:**
  ```python
  total_units = sum(item.quantity for item in self._inv._items.values())
  if total_units == 0:
      return 0.0
  return self._inv.get_total_value() / total_units
  ```

- **ตำแหน่ง:** ทุกเมธอดใน `InventoryService` ที่เรียกใช้ `self._inv._items`
- **ปัญหาคืออะไร:** ตัวแปร `_items` ในคลาส `Inventory` ขึ้นต้นด้วยขีดล่าง `_` ซึ่งเป็นข้อตกลง (Convention) ของ Python ว่าเป็น Private/Internal state ห้ามให้คลาสภายนอกเข้าถึงหรือแก้ไขโดยตรง การที่ `InventoryService` ข้ามไปแก้ไข `item.quantity` โดยตรง ทำให้ข้าม Validation ใน `Inventory.sell()` และ `Inventory.restock()`
- **ข้อเสนอแก้:** คลาส `Inventory` ควรเตรียมเมธอดสาธารณะ (Public API) เช่น `get_item(name)` หรือ `list_items()` ให้บริการแทนการให้คลาสอื่นล้วงเข้าถึง `_items` โดยตรง
